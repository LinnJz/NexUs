# ADR-0001: Skill 层级结构设计

## 状态

Accepted

## 上下文

NexUs 项目需要一套标准化的 skill 文档体系，使大语言模型（LLM）能快速对齐项目上下文，并按需加载对应知识来执行三类任务：**修复 Bug**、**扩展功能**、**新增控件**。

初始状态是 `skill/` 目录下三个扁平大文档：

- `NexUs-Control-Rules.md`（1249 行）—— 涵盖架构、主题、导航、窗口、样式、动画、Graphics、21+ 节的全部规则
- `NexUs-New-Control-Template-Rules.md`（915 行）—— 新增控件全流程
- `SKILL.md`（415 行）—— ElaWidgetTools API 参考

问题在于：LLM 上下文窗口有限。加载全部 ~2600 行规则来执行一个具体的"修复主题切换 bug"任务，会挤压有效推理空间；而按需加载又缺乏标准化的入口和导航。

存在三种备选方案：

### 方案 A：保持扁平，单一巨型文件

将所有规则合并为一个 2600+ 行的超集文件。优点是不需要拆分决策，缺点是 LLM 必须全部加载或依赖检索才能命中相关段落，token 浪费严重。

### 方案 B：按子系统拆分目录

将规则拆解为若干按关注点（主题、导航、窗口、控件开发）分类的小 skill 文件，每个 200-500 行。通过一个入口文件（0-align.md）索引，LLM 根据任务类型选择性加载。

### 方案 C：按层级拆分（learning path）

按学习顺序分层——入门（项目简介）、进阶（核心子系统规则）、高级（复杂场景模板）。优点是渐进式学习，但增加了跨 skill 跳转时的上下文断裂风险。

## 决策

采用 **方案 B：按子系统拆分目录**。

具体结构：

```
skill/
├── 0-align.md                   # 入口索引，指向各 skill
├── theme/SKILL.md               # 主题系统规则
├── navigation/SKILL.md          # 导航路由规则
├── window/SKILL.md              # 窗口层规则
├── controls/
│   ├── new-control.md           # 新增控件模板
│   ├── add-feature.md           # 扩展现有控件
│   └── fix-bug.md               # 修复控件 Bug
└── reference/
    ├── api-reference.md         # API 文档
    └── elawidgettools-api.md    # 上游 API 参考
```

每个 skill 文件遵循统一模板：适用场景 → 相关概念 → 核心规则 → 代码模式 → 风险点 → 验证清单。

## 理由

1. **按需加载**：LLM 仅加载任务对应的 skill（200-500 行），而非整套规则（2600+ 行）。
2. **关注点分离**：主题、导航、窗口、控件开发各自独立，修改一个不影响其他。
3. **可扩展**：新增子系统只需在 `0-align.md` 加一行索引并新建目录。
4. **验证闭环**：每个 skill 内嵌验证清单，使 LLM 输出可自查。

## 不选理由

- **方案 A**（扁平合并）：token 效率最低。2600+ 行规则即使全部加载，LLM 对远距离相关性的保持能力也会下降。
- **方案 C**（按层级拆分）：引入不必要的"学习顺序"概念。LLM 不需要渐进式学习，它需要的是任务驱动的最小按需知识包。

## 后果

- **正面**：skill 文件可独立维护、独立版本控制、按需测试。
- **正面**：CONTEXT.md 与 skill 职责清晰——CONTEXT.md 只做术语定义，skill 承载实现规则和模板。
- **负面**：跨 skill 决策（如"新增一个既是页面又是导航输入的控件"）需要同时加载多个 skill，增加了多文件协调的复杂度。对此，`0-align.md` 的索引表通过"适用场景"列来指导组合加载。
- **负面**：需要维护 `0-align.md` 的索引与实际 skill 目录的一致性，避免死链。
